# Patterns and Templates Specification

## 1. Declarative definition grammar

The notation below uses an EBNF sketch. The parser specification and fixtures
will fix token details before implementation.

```text
macro-definition  ::= export? recursion? "syntax" macro-name ":" category
                      shadow-clause? "{" macro-rule+ "}"
recursion         ::= "rec"
shadow-clause     ::= "shadows" "core"
macro-rule        ::= "rule" pattern binding-clause* "=>" template

class-definition  ::= export? "syntax" "class" name
                      "{" field-declaration class-rule+ "}"
field-declaration ::= "fields" "{" field (";" field)* ";"? "}"
field             ::= name ":" capture-type optional-marker?
class-rule        ::= "rule" pattern refinement-clause*

pattern           ::= "{" pattern-sequence "}"
template          ::= "{" template-sequence "}"
```

Macro names may use one identifier or one explicitly grouped punctuation
sequence. Categories come from the fixed syntax-consumer registry.

## 2. Pattern nodes

```ts
type PatternNode =
  | LiteralPattern
  | CapturePattern
  | GroupPattern
  | SequencePattern
  | ChoicePattern
  | RepeatPattern
  | OptionalPattern
  | ClassCallPattern
  | LookaheadPattern;
```

Version 1 does not expose negative arbitrary lookahead. `LookaheadPattern`
supports a fixed set of token and boundary predicates generated by syntax-class
syntax.

## 3. Literal matching

- Punctuation and keywords compare token kind plus raw spelling when spelling
  distinguishes tokens.
- Delimiters compare group kind and match their children against the nested
  pattern.
- Identifier literals default to spelling comparison.
- A declared binding literal compares resolved binding identity. Macro imports
  use this form for keywords owned by a macro library.
- Trivia does not participate.

## 4. Captures and syntax classes

`$x:expr` calls class `expr` at the current cursor. A successful capture stores:

```ts
interface CaptureLeaf {
  id: CaptureId;
  classId: SyntaxClassId;
  syntax: SyntaxSequence;
  fields: CaptureRecord;
  origin: OriginId;
}
```

A user syntax class declares its public fields. Class rules may use different
internal captures, but each successful rule must return all required fields.
Optional fields use an explicit optional declaration.

Field access uses `$capture.field`. Repeated capture access retains sequence
dimensions: `$methods.name` has the same outer dimension as `$methods`.

## 5. Rule and choice behavior

- Ordinary macro rules run in source order, followed by explicitly marked
  `fallback rule` declarations in their source order.
- The matcher commits after one rule consumes a complete invocation accepted by
  the surrounding syntax consumer.
- A failed rule restores the cursor and capture state.
- A syntax-class rule follows the same ordered policy.
- The definition compiler warns when it proves a later rule unreachable.
- Authors MUST mark low-priority catch-all behavior with `fallback rule`.
  Fallback is an explicit priority class, not a heuristic inferred from pattern
  shape. ADR-0003 records this decision.

The matcher ranks failures by farthest source position, then by pattern
specificity. It merges expectations at the same position and retains the macro
definition origins that produced them.

## 6. Repetition

```text
$($x:expr),*   zero or more
$($x:expr),+   one or more
$($x:expr)?    optional
```

The AST stores body, separator, minimum, maximum, and repetition depth. The
pattern compiler rejects a body that can match without cursor progress.

Captures have a shape:

```ts
type CaptureShape = LeafShape | SequenceShape;
interface SequenceShape {
  kind: "sequence";
  depth: number;
  element: CaptureShape;
  cardinalityGroup: CardinalityGroupId;
}
```

Captures introduced within the same repetition share a cardinality group at
that depth. Template repetition over several captures requires compatible groups
and equal runtime lengths. Nested repetitions compare one dimension at a time.

Separators belong to the pattern and do not enter captures unless captured. A
template can emit a chosen separator.

## 7. Matcher program

The pattern compiler lowers patterns to instructions:

```ts
type Instruction =
  | { op: "literal"; token: LiteralKey; next: Pc }
  | { op: "group"; delimiter: DelimiterKind; body: Pc; next: Pc }
  | { op: "class"; classId: SyntaxClassId; capture: Slot; next: Pc }
  | { op: "split"; first: Pc; second: Pc }
  | { op: "repeat-enter"; repetition: RepetitionId; body: Pc; exit: Pc }
  | { op: "repeat-commit"; repetition: RepetitionId; loop: Pc; next: Pc }
  | { op: "accept" };
```

The runtime uses an explicit work stack. It memoizes failed states keyed by
`(program, pc, cursor identity, environment epoch, repetition shape)`. It charges
one matcher step per instruction and syntax-consumer step per consumer call.

## 8. Refinements

Version 1 supplies pure refinements:

- identifier spelling equals, starts with uppercase/lowercase, or belongs to a
  finite set;
- token kind belongs to a finite set;
- capture followed or preceded by a literal boundary;
- capture matched a named alternative;
- repetition length comparison with an integer literal;
- delimiter kind.

The macro-language compiler lowers refinements into fixed IR. Macro source cannot
call host functions.

## 9. Template nodes

```ts
type TemplateNode =
  | LiteralTemplate
  | CaptureTemplate
  | GroupTemplate
  | SequenceTemplate
  | RepeatTemplate
  | ConditionalTemplate
  | FoldTemplate
  | HygieneOperationTemplate
  | GeneratedDefinitionTemplate;
```

Literal template syntax receives the invocation introduction scope. Capture
templates copy syntax and scopes, then attach a copied origin. Group templates
construct balanced syntax groups before printing.

## 10. Template repetition

A repeated template establishes one dimension. Captures referenced at that
dimension select the current element. Captures from outer dimensions remain
available. A capture from a deeper dimension requires nested template
repetition.

The validator rejects:

- a repeated template with no driving repeated capture;
- captures with incompatible cardinality groups;
- access to a deeper capture without enough repetition levels;
- a separator outside a repetition;
- an optional capture used without conditional handling.

## 11. Conditional templates and folds

Conditionals inspect matched alternative tags, optional presence, or fixed
refinement results. They cannot inspect runtime TypeScript values.

The declarative surface uses fixed predicates and syntax branches:

```text
#if(present $maybe) { present syntax } #else { absent syntax }
#if(alternative $value "branch-name") { selected syntax }
```

Capture field paths are permitted in both predicates. The alternative tag is
definition metadata produced by pattern matching, not a runtime string value.

A fold processes one captured sequence:

```text
#fold($items, init: { initial syntax }) {
  ($acc, $item, $index) => { next syntax }
}
```

The compiler lowers the body to template IR. `$index` is a compile-time integer
literal syntax value. The fold charges one template step per element and cannot
perform I/O or invoke host functions.

`#count($capture)` computes the total number of leaves in a captured repetition
and emits the result as numeric-literal syntax. It is charged against the
template-step budget and records the capture and count in expansion traces.

The parameter list is fixed to `($acc, $item, $index)`. `$acc` splices the
previous evaluated accumulator, `$item` selects the current capture element and
its declared fields, and `$index` emits the zero-based compile-time index. The
body becomes the complete next accumulator. Empty input returns the initial
template unchanged.

## 12. Binding clauses

Each binding clause refers to capture paths and has a repetition alignment:

```ts
interface BindingClause {
  binders: CapturePath;
  region: CapturePath;
  space: SyntaxSpace;
  kind: "lexical" | "recursive" | "sequential";
}
```

`sequential` means element `i` binds in elements after `i` and the final result.
This form supports a nonrecursive `do` representation if the macro chooses to
match all steps at once. Recursive `do` rules can use one lexical clause per
step.

## 13. Definition-time validation order

1. parse the definition;
2. resolve syntax classes and binding literals;
3. infer capture shapes and repetition depths;
4. validate class result fields;
5. compile the matcher;
6. validate template capture use;
7. validate binding clauses;
8. run reachability and progress analysis;
9. assign stable definition and rule IDs;
10. serialize declarative IR.

No malformed definition reaches invocation-time matching.

## 14. Required examples

- `Bind` and `BindAll` classes with optional semicolons;
- threading recursion with comma-separated calls;
- ADT constructors with nested constructor-argument repetition;
- protocol methods with exported name and argument fields;
- mixfix method segments;
- identifier-case refinement in a match pattern class;
- a fold that creates positional field checks;
- each definition-time failure listed in sections 6, 10, and 12.
